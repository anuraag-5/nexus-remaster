This document records the agreed architecture, the reasoning behind it,
the current implementation evidence, and decisions that are still open.
It is intended to let a future engineer (or a future ChatGPT conversation)
reconstruct the project without relying on conversational memory.

Status vocabulary:
  DECIDED      Explicitly agreed architecture decision.
  IMPLEMENTED  Code/schema is reported as present.
  VERIFIED     Supported by a recorded successful test/build/run.
  PLANNED      Agreed or intended, but not implemented yet.
  OPEN         Must be designed or verified before implementation.
  DEFERRED     Intentionally excluded from the current MVP.

Never upgrade PLANNED to IMPLEMENTED or IMPLEMENTED to VERIFIED without
evidence. A passing unit test is not proof of deployment or production
readiness. This document should be updated whenever a meaningful
architecture decision changes.

The uploaded development log is a progress snapshot, not the complete
architecture. This file is the deeper design record; the development log
should remain the concise execution checklist.

1. PRODUCT GOAL AND SCOPE
======================================================================

Nexus Remaster is a website-monitoring SaaS. A customer creates monitors
for HTTP/HTTPS endpoints and selects one or more monitoring regions.
Nexus periodically checks each monitor from the selected regions, records
the results, computes availability/latency information, detects incidents,
and presents the information in a dashboard.

MVP target capabilities:
  - Workspace-based accounts and authorization.
  - Monitor creation/listing and region selection.
  - Secure HTTP/HTTPS checks against user-provided destinations.
  - Independent regional probes from India and the USA.
  - Durable scheduling and dispatch.
  - Redis + BullMQ for regional job delivery and worker coordination.
  - Separate regional worker deployments that actually execute checks
    from their respective regions.
  - Durable check history and per-region status/latency.
  - Recovery from duplicate delivery, process crashes, Redis outages,
    and temporary database pressure.
  - Basic incidents/notifications.
  - Free/Pro entitlements, with Stripe test-mode billing and verified,
    idempotent webhooks.
  - Deployment, observability, tests, documentation and a credible demo.

Initial regions:
  - ap-south-1: Mumbai, India.
  - us-east-1: Northern Virginia, USA.

Deployment topology decision:
  - Regional workers are deployed in India and USA.
  - API, primary PostgreSQL and Redis are central services for the MVP.
  - This is NOT active-active multi-region database infrastructure.
  - A worker's configured region is not proof of its physical location;
    deployment location must be verified operationally.

Out of current MVP scope:
  - Redis dashboard/analytics caching.
  - Plan-based queue priorities.
  - Additional monitoring regions beyond India and USA.
  - Active-active PostgreSQL or multi-region control plane.
  - Exactly-once execution claims.

2. ARCHITECTURAL PRINCIPLES
======================================================================

2.1 PostgreSQL is the durable source of truth.
Business state, monitor configuration, region/probe configuration,
logical check executions, check results, dispatch intent, incidents,
subscriptions and entitlements belong in PostgreSQL.

2.2 Redis/BullMQ is delivery and execution infrastructure.
Redis/BullMQ coordinates jobs, retries, delays, worker concurrency,
rate limiting and stalled-job recovery. It is not the canonical store
for monitor state or historical check results.

2.3 Delivery is at-least-once.
A job may be delivered more than once. The design must tolerate duplicate
publication, duplicate delivery, worker retry and process restart.
Do not claim exactly-once delivery or exactly-once execution.

2.4 Idempotency is enforced at the database boundary.
A deterministic identity for a logical scheduled execution, unique
constraints, conditional state transitions and execution fencing prevent
duplicate or stale deliveries from creating duplicate business effects.

2.5 Never hold a database transaction open during an external HTTP check.
Claim/prepare work in a short transaction, commit, perform the network
request, then persist the result in another short transaction.

2.6 Bound every resource.
Scheduler batch size, publisher batch size, worker concurrency, per-region
queue throughput, per-target request rate, HTTP timeouts and PostgreSQL
pool sizes must all have explicit limits.

2.7 Fail closed on destination security.
A URL is not safe merely because it passed initial parsing. Every redirect
must be revalidated; DNS results must be checked; the actual connection
must use a validated address; outbound network restrictions are a further
defence layer.

2.8 Distinguish a logical check from its delivery attempts.
BullMQ retries are attempts to complete the same logical scheduled check.
They must not be counted as separate scheduled monitoring samples or
inflate uptime/availability statistics.

The scheduler, publisher and reconciler may initially be modules in one

The API must not perform monitoring HTTP checks in request handlers.
The scheduler must not perform monitoring HTTP checks.
Workers execute checks; the database records durable outcomes.

4. COMPONENT RESPONSIBILITIES
======================================================================

4.1 Frontend
  - Next.js application.
  - Clerk authentication.
  - Calls API using a verified Clerk bearer token.
  - Displays workspace monitors, per-region status, latency and history.
  - Must treat API responses as authoritative; it must not enforce
    subscription limits only in the browser.

4.2 API
  - Express 5 + TypeScript.
  - Authenticates requests and enforces workspace membership.
  - Validates input and applies server-side authorization.
  - Creates monitors and selected regional probes transactionally.
  - Exposes monitor/check/incident/billing data.
  - Does not enqueue directly from ordinary monitor-create requests unless
    a specific use case is designed; periodic monitoring is scheduled by
    the durable scheduler/outbox path.
  - Does not own worker execution.

4.3 PostgreSQL
  - Durable source of truth.
  - Stores workspaces, members, monitors, region catalog, regional probes,
    check results, dispatch/execution state, incidents and billing state.
  - Enforces referential integrity and uniqueness.
  - Uses migrations for all schema changes.
  - All query inputs are parameterized.
  - Database transactions are short and do not span network checks.

4.4 Scheduler
  - Finds due enabled regional probes, not just monitor-level schedule rows.
  - Respects monitor enabled state, probe enabled state and region enabled
    state.
  - Claims bounded batches safely when multiple scheduler instances run.
  - Creates a durable logical execution identity and outbox dispatch intent
    in the same PostgreSQL transaction.
  - Advances the probe's next_check_at according to the chosen scheduling
    policy in that transaction.
  - Does not depend on Redis being available to preserve the scheduling
    decision.
  - Does not perform HTTP requests.

4.5 Transactional outbox
  - Makes dispatch intent durable in the same transaction as the logical
    execution/scheduling state change.
  - Prevents the failure window where the scheduler advances a schedule
    but loses the corresponding queue message.
  - Is the durable hand-off between PostgreSQL and Redis/BullMQ.
  - Exact table names, columns, indexes and state transitions remain OPEN
    until the existing migrations and schema are reviewed together.

4.6 Reliable publisher
  - Reads a bounded set of eligible outbox records.
  - Claims work with concurrency-safe database semantics and a finite
    lease/claim timeout.
  - Publishes a versioned job to the queue matching the execution region.
  - Uses deterministic job identity so ambiguous publication can be retried
    without intentionally creating a new logical execution.
  - Marks dispatch state only after the queue publication call reports
    success.
  - If the process crashes after Redis accepted a job but before PostgreSQL
    records publication, it may publish again. This is expected; worker-side
    idempotency handles it.
  - Retries transient Redis errors with bounded backoff.
  - Does not mark a record permanently complete merely because an attempt
    was made.
  - Does not rely on BullMQ job retention as the only deduplication control.

4.7 Redis + BullMQ
  - Redis is the shared BullMQ backing service.
  - Separate queues for India and USA, e.g.:
      nexus-checks-ap-south-1
      nexus-checks-us-east-1
  - Job payloads are small, versioned and contain identifiers, not
    authoritative monitor configuration.
  - Workers should load current monitor/probe configuration from PostgreSQL
    before executing, or validate a versioned immutable execution snapshot
    if that design is later chosen.
  - BullMQ provides job lifecycle, retries/backoff, delayed work, stalled
    job recovery, worker coordination, regional queue limiting and
    concurrency controls.
  - Redis loss must not erase the durable intent in PostgreSQL.

4.8 Regional workers
  - Separate process entry points/deployments for India and USA.
  - Each worker consumes only its assigned regional queue.
  - Verify the job's region matches the worker's configured region.
  - Load and validate current execution/monitor/probe state.
  - Execute the secure HTTP checker from the worker's real deployment region.
  - Persist the result and update regional probe state in a short,
    idempotent PostgreSQL transaction.
  - Enforce bounded concurrency and a separately bounded DB pool.
  - Shut down gracefully: stop accepting new work, allow or safely abandon
    active work within a defined deadline, close BullMQ/Redis and DB pools.
  - A worker crash must not permanently lose a logical execution.

4.9 Reconciler
  - Compares durable PostgreSQL execution/dispatch state with expected
    scheduling and delivery state.
  - Detects due probes without a valid active logical execution.
  - Detects outbox records whose publication lease expired or whose state
    is inconsistent.
  - Detects executions stuck beyond their expected deadline.
  - Repairs/re-dispatches work safely using the same logical execution
    identity where appropriate.
  - Must not blindly create a new logical execution for every retry.
  - Reconciliation rules and terminal-state policy are OPEN and must be
    specified before implementation.

4.10 Observability
  - Structured Pino logs with correlation identifiers:
    monitor_id, probe_id, execution_id, outbox_id, queue/job id, region.
  - Metrics for scheduler lag, due probes, outbox age, publish failures,
    queue depth, oldest queued job, worker active count, check duration,
    check outcomes, retry count, DB pool saturation and reconciliation
    repairs.
  - Health/readiness must distinguish process liveness from dependency
    readiness.
  - Never log secrets, authorization tokens or sensitive request headers.

5. DATA MODEL — CURRENT FACTS AND PLANNED ENTITIES
======================================================================

5.1 Implemented schema (as of 2 November 2026, based on project notes)

workspaces
  - UUID primary key.
  - name, created_at, updated_at.

workspace_members
  - workspace_id FK.
  - auth_provider_user_id.
  - role: owner/admin/member.
  - composite primary key (workspace_id, auth_provider_user_id).

monitors
  - UUID primary key.
  - workspace_id FK.
  - name, url.
  - interval_seconds (30–86400; default 300).
  - timeout_ms (1000–60000; default 10000).
  - is_enabled.
  - transitional monitor-level current_status, next_check_at,
    last_checked_at fields.
  - created_at, updated_at.

monitor_regions
  - region code, country code, display name, is_enabled, created_at.
  - Initial codes: ap-south-1 and us-east-1.

monitor_probes
  - UUID id.
  - monitor_id FK.
  - region_code FK.
  - is_enabled, current_status, next_check_at, last_checked_at,
    created_at, updated_at.
  - unique(monitor_id, region_code).
  - partial due-work index on (region_code, next_check_at) for enabled rows.

monitor_checks
  - Historical check records now reference a regional probe_id.
  - Exact full column definitions and constraints must be re-read from
    the applied migration before designing dependent schema.

Historical check migration note:
  - Existing historical checks were assigned to the India probe by
    migration convention. Their actual historical origin was unknown.
  - Do not present those historical records as verified India-origin
    measurements.

5.2 Planned data concepts (not yet implemented / exact schema OPEN)

Logical execution:
  - One intended scheduled check for one probe at one scheduled time.
  - Has a deterministic identity/uniqueness rule.
  - Owns the result and terminal outcome of that logical check.
  - Delivery attempts are children/metadata of this logical execution,
    not new monitoring samples.

Outbox dispatch record:
  - Durable intent to publish a logical execution to its regional queue.
  - Links to execution and region.
  - Needs a retryable publication lifecycle, claim/lease semantics,
    timestamps and bounded error metadata.
  - Exact states and fields are not finalized.

Attempt/fencing information:
  - Needed to stop an old or slow worker from overwriting a newer accepted
    outcome.
  - Must define ownership/lease or fencing-token semantics before coding.
  - Do not add speculative claim_token/lease_expires_at/attempt_count
    columns to monitor_probes as a shortcut. That earlier proposal was
    explicitly rejected as premature.

5.3 Schema migration rules
  - Never edit an already-applied migration.
  - Create a new migration for schema changes.
  - Inspect the full applied migration source and actual database schema
    before writing dependent migrations.
  - Do not drop transitional monitor-level status/schedule columns until
    API/UI consumers have moved to probe-level state and a migration plan
    exists.

6. END-TO-END SCHEDULING AND EXECUTION LIFECYCLE
======================================================================

The following is the intended logical flow. Exact SQL and state names are
OPEN until the outbox design milestone is completed.

Step 1 — Discover due work
  Scheduler selects enabled probes whose next_check_at is due, while
  respecting enabled monitor and enabled region state.

Step 2 — Claim and create durable intent
  In a short transaction, scheduler safely claims a bounded batch,
  creates one logical execution per due probe/time slot, creates the
  corresponding outbox record, and advances next_check_at.
  Concurrent scheduler instances must not create duplicate logical
  executions for the same scheduled slot.

Step 3 — Commit before queue I/O
  The transaction commits. The outbox record now survives scheduler
  process death and Redis unavailability.

Step 4 — Publish
  Publisher claims eligible outbox rows and sends a versioned job to the
  appropriate regional BullMQ queue.

Step 5 — Record publication
  Publisher records successful publication in PostgreSQL. If the publisher
  dies between queue acceptance and this database update, the job may be
  published again. This is an expected at-least-once failure mode.

Step 6 — Consume
  Regional worker receives job, checks schema version and region, loads
  durable execution/probe/monitor state, and rejects invalid, disabled,
  expired or already-terminal work according to the agreed state rules.

Step 7 — Execute
  Worker performs the HTTP request using the secure checker. No DB
  transaction remains open during DNS/network/TLS/HTTP operations.

Step 8 — Persist result
  Worker begins a short transaction, verifies execution identity/fencing,
  inserts or finalizes the result idempotently, updates probe status and
  timestamps, and commits.

Step 9 — Retry or terminal outcome
  Transient failures may be retried with exponential backoff and jitter
  within a bounded attempt/time policy. A retry is another attempt for the
  same logical execution. Permanent policy/configuration errors should not
  be retried indefinitely. Exact classification and terminal rules remain
  OPEN.

Step 10 — Reconcile
  Reconciler repairs durable work that did not progress because of process
  failure, queue outage, expired claims or inconsistent state.

Scheduling policy OPEN:
  - Whether next_check_at is based on scheduled cadence or completion time.
  - How missed intervals are handled after a long outage.
  - Whether missed slots are skipped or coalesced.
  - How interval changes affect already-created executions.
  These must be decided explicitly; do not accidentally create a large
  catch-up storm after downtime.

7. RELIABILITY, FAILURE MODES AND GUARANTEES
======================================================================

7.1 Redis outage
  - Scheduler can continue writing durable outbox intent to PostgreSQL,
    subject to configured backlog limits.
  - Publisher retries when Redis returns.
  - Queue backlog/outbox age rises and must be observable.
  - Backpressure eventually slows or pauses additional dispatch to avoid
    unbounded backlog.
  - Redis recovery must not require reconstructing lost business intent
    from memory.

7.2 Publisher crash before publish
  - Outbox claim expires or is released.
  - Another publisher retries the same outbox record.

7.3 Publisher crash after Redis accepts, before DB acknowledgement
  - Same logical job may be published again.
  - Deterministic job identity reduces duplicates where BullMQ recognizes
    the existing job, but DB idempotency remains mandatory.
  - Do not assume BullMQ deduplication is permanent after job removal.

7.4 Worker crash before HTTP request
  - BullMQ stalled-job recovery/retry or reconciliation causes another
    attempt.
  - Durable execution remains identifiable.

7.5 Worker crash during HTTP request
  - The request may have reached the target even though no result was
    persisted. The retry can issue another GET.
  - Monitoring checks must use safe, non-mutating HTTP methods (normally
    GET or HEAD as explicitly selected) and a bounded timeout.
  - The system cannot promise the target observed exactly one request.

7.6 Worker crash after HTTP response, before result commit
  - A retry may repeat the check.
  - Only one accepted logical result should affect durable check history
    and uptime calculations.

7.7 Duplicate delivery
  - Multiple deliveries can refer to the same execution_id.
  - Database uniqueness/conditional transitions prevent duplicate
    check-result effects.
  - A worker seeing a terminal execution should acknowledge/no-op safely.

7.8 Stale worker / overlapping attempts
  - A slow worker may finish after a newer attempt.
  - Fencing or conditional ownership checks prevent stale completion from
    overwriting the accepted result.
  - Exact fencing design is OPEN; must be settled before implementation.

7.9 PostgreSQL outage
  - API readiness and worker readiness should reflect inability to persist.
  - Workers must not report successful completion if result persistence
    failed.
  - Queue retry/reconciliation must recover without losing durable intent.
  - DB pools and retries must be bounded to avoid a retry storm.

7.10 Database overload / queue backlog
  - Bound worker concurrency independently from DB pool size.
  - Use short result transactions.
  - Limit scheduler and publisher batch sizes.
  - Apply queue-aware backpressure based on backlog and resource pressure.
  - Avoid scaling workers solely based on queue depth if PostgreSQL is
    already saturated.

7.11 Regional rate limits and per-target protection
  - Regional queue-level limiter controls regional throughput.
  - It does not by itself protect one destination from concentrated checks.
  - Add per-target limits/serialization or a shared target budget so one
    website cannot receive excessive concurrent requests from many jobs
    or regions.
  - Define target identity normalization carefully (hostname/port and
    redirect destination considerations).
  - Rate-limit state must be coordinated across worker processes if the
    guarantee is global rather than per-process.

7.12 Delivery guarantee wording
  Correct: "At-least-once delivery with idempotent database effects."
  Incorrect: "Exactly-once job execution."
  A network request may be repeated after an ambiguous crash. The system
  guarantees controlled durable accounting, not exactly one outbound
  packet/request.

8. RETRIES, BACKOFF, LIMITS AND BACKPRESSURE
======================================================================

Agreed capabilities:
  - Retry transient failures.
  - Exponential backoff with jitter.
  - Stalled-job recovery.
  - Regional rate limiting.
  - Per-target protection.
  - Bounded worker concurrency.
  - Bounded DB connection pools.
  - Queue-aware backpressure.
  - Idempotent result persistence and reconciliation.

Still to specify numerically:
  - Max attempts and total execution deadline.
  - Base/max retry delay and jitter range.
  - HTTP timeout budget vs BullMQ lock/stall settings.
  - Worker concurrency per region.
  - DB pool maximum per process and total deployment budget.
  - Scheduler/publisher batch sizes and polling cadence.
  - Queue backlog thresholds and hysteresis for pause/resume.
  - Per-target concurrency/rate window.
  - Stalled-job detection settings.

All numerical limits must be derived from the deployment's actual resource
budget and tested under load. Do not copy arbitrary production-looking
numbers into configuration without measuring.

Retries should distinguish:
  - Transient infrastructure errors: likely retry.
  - Target timeout / transient network error: retry within bounded policy.
  - Invalid URL / forbidden destination / policy violation: permanent,
    do not retry.
  - Invalid or stale execution state: acknowledge/no-op or reconcile,
    do not loop forever.
  - PostgreSQL persistence failure: do not acknowledge successful work;
    let a bounded retry/recovery path handle it.

Exact error codes and retry classification are OPEN.

9. SECURITY ARCHITECTURE
======================================================================

9.1 Authentication and authorization
  - Clerk authenticates users.
  - API verifies tokens server-side.
  - Workspace membership is checked in service/database layer.
  - Never trust workspace IDs or roles supplied by the browser.
  - Subscription entitlements are enforced server-side.

9.2 URL policy (implemented baseline)
  - HTTP/HTTPS only.
  - Reject URL credentials.
  - Reject IP-literal hosts.
  - Reject local/internal suffixes (.localhost, .local, .internal,
    .test, .home.arpa, .lan).
  - Reject non-standard ports.
  - Strip URL fragments.
  - Require a hostname in the current FQDN-style policy.

9.3 DNS/IP policy (implemented baseline)
  - Resolve target addresses.
  - Reject empty results and non-public address results using ipaddr.js
    classification.
  - Connect to a validated/pinned address to reduce DNS-rebinding risk.
  - Revalidate every redirect destination.
  - Prevent HTTPS-to-HTTP downgrade.

9.4 Security work still OPEN
  - Verify TLS certificate identity against the original hostname when
    connecting to a pinned IP; explicitly use correct hostname verification.
  - Ensure timeout cancellation aborts the underlying DNS/network operation,
    not merely the promise waiting for it.
  - Review all special-purpose IPv4/IPv6 ranges; a generic "unicast"
    classification may not be sufficient.
  - Use stable error codes rather than parsing error-message strings.
  - Test redirects, address fallback, response destruction, timer cleanup,
    TLS behavior and real network behavior.
  - Add infrastructure-level outbound network controls/egress firewall.
  - Review DNS rebinding and resolver behavior.
  - Add abuse controls, target limits and request header restrictions.

9.5 Request behavior
  - Monitoring requests must be bounded by timeout and response-size limits.
  - Do not forward user cookies, authorization headers or ambient credentials.
  - Avoid request methods with side effects.
  - Do not follow redirects without applying the full destination policy.
  - Do not expose internal DNS/IP or stack details in customer-facing errors.

Do not describe the checker as production-hardened until the open items and
network-level tests have been completed.

10. BILLING AND ENTITLEMENTS

  - Server validates monitor count, check interval, enabled regions,

11. DEPLOYMENT TOPOLOGY
======================================================================

MVP topology:
  - Next.js frontend deployment.
  - Express API deployment.
  - Central PostgreSQL.
  - Central Redis/BullMQ backing service.
  - Scheduler/publisher/reconciler process (may initially be co-located).
  - India worker deployment in ap-south-1.
  - USA worker deployment in us-east-1.

Deployment requirements:
  - Separate environment configuration for API, scheduler/publisher and
    each regional worker.
  - Region identity is explicit and validated at startup.
  - Worker queue name is derived from a fixed allow-listed region mapping,
    not arbitrary user input.
  - Secrets supplied through deployment secret management, never source.
  - Graceful shutdown and health/readiness endpoints.
  - Verify worker egress IP/location from each region.
  - Verify Redis/PostgreSQL network access and TLS settings for deployment.
  - Backups and migration/rollback procedure for PostgreSQL.
  - Redis persistence/availability expectations documented; PostgreSQL
    remains the durable recovery source.

This topology is not active-active. Central database/Redis availability
remains a dependency for both regions.

not merely process existence.

14. DECISIONS, ALTERNATIVES AND TRADE-OFFS
======================================================================

D-001: PostgreSQL is durable source of truth.
Reason: monitor/business state and recovery intent must survive queue loss.
Trade-off: scheduler/outbox/reconciliation require additional DB design.

D-002: Use BullMQ/Redis rather than direct PostgreSQL polling by workers.
Alternative considered: workers claim due rows directly with
FOR UPDATE SKIP LOCKED and implement leases/retries themselves.
Reason for selected design: BullMQ supplies job distribution, retry/backoff,
delayed jobs, stalled-job recovery, regional queues, rate limiting and
worker coordination. PostgreSQL remains canonical.
Trade-off: Redis is another dependency and an outbox is required to bridge
the DB/queue boundary reliably.
Important nuance: direct DB polling is a valid architecture. It was not
selected; do not describe it as inherently incorrect or unsafe.

D-003: Scheduler is separate from HTTP check execution.
Reason: schedule/dispatch work must not be blocked by slow target requests.

D-004: Separate regional queues and workers.
Reason: checks must originate from India and USA, with region-specific
throughput and deployment control.

D-005: At-least-once delivery + idempotent DB effects.
Reason: network/process failure makes exactly-once execution unrealistic.
The durable result must be safe under duplicate attempts.

D-006: Transactional outbox.
Reason: avoid losing dispatch intent between advancing a schedule and
publishing to Redis.

D-007: Queue-aware backpressure and independent resource limits.
Reason: queue depth alone must not drive unbounded worker/DB load.

D-008: Per-target protection in addition to regional rate limiting.
Reason: a regional limiter does not prevent concentrated requests to one
target across workers or regions.

D-009: Defer dashboard caching, plan priorities and extra regions.
Reason: protect the MVP deadline and prioritize correctness of the core
monitoring path.

D-010: Do not add speculative lease fields directly to monitor_probes.
Reason: execution ownership, outbox publication and worker fencing must be
designed as one coherent state model first.

15. OPEN DESIGN QUESTIONS — MUST RESOLVE BEFORE OUTBOX MIGRATION
======================================================================

These are intentionally not silently decided by this document:

A. Logical execution identity:
   - Which fields define one scheduled slot?
   - Is identity based on probe_id + scheduled_for timestamp, plus a
     generation/version to handle interval/configuration changes?
   - What uniqueness constraint prevents concurrent scheduler duplicates?

B. Execution state machine:
   - Which states are required (e.g. scheduled, queued, running,
     succeeded/failed/terminal/expired)?
   - Which transitions are legal, and which actor may perform each?
   - How are cancellation/disabled monitor changes handled?

C. Outbox state machine:
   - Pending -> claimed/publishing -> published?
   - How are expired claims recovered?
   - What is the policy for permanent publication failures?
   - Are publish attempts stored on the outbox row or in a separate table?

D. Worker ownership/fencing:
   - Is there a lease per execution?
   - How is a monotonically increasing fencing token created?
   - How does a worker prove it still owns the right to finalize?
   - How are late responses from stale attempts discarded?

E. Retry policy:
   - Which errors are transient/permanent?
   - How many attempts and what total deadline?
   - Does BullMQ own retry timing, while PostgreSQL records attempt state?
   - How does reconciliation interact with BullMQ retries?

F. Scheduling semantics:
   - Schedule from due time or completion time?
   - Skip/coalesce missed intervals after downtime?
   - What happens when monitor interval or regions change?
   - How are duplicate scheduler runs serialized?

G. Result model:
   - Does monitor_checks represent one logical execution result, or one
     row per network attempt plus a separate accepted final result?
   - How are failed attempts represented without distorting uptime?
   - What exact uniqueness and foreign-key rules are needed?

H. Queue payload:
   - Minimum identifiers and schema version.
   - Whether config is loaded live or captured as an immutable snapshot.
   - How stale jobs are detected.

I. Reconciliation:
   - Which durable states are scanned?
   - How are missing jobs re-published?
   - How are stuck executions expired/retried?
   - How is repair bounded to avoid a thundering herd?

J. Backpressure and target protection:
   - Which metrics/thresholds trigger pause or slowdown?
   - Is per-target coordination global across regions?
   - What is the normalized target key and fairness policy?

No migration should be written until these questions are resolved sufficiently
to produce a coherent schema and transition design.
