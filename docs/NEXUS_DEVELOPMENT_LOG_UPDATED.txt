## 4. Agreed architecture

See `NEXUS_ARCHITECTURE.txt` for the full component design, state-machine questions, failure analysis, security model, deployment topology and decision history.

Current end-to-end target:

**PostgreSQL → Scheduler → Transactional Outbox → Reliable Publisher → Redis/BullMQ regional queues → Regional Workers → PostgreSQL**

A reconciler repairs missing or stuck work using durable PostgreSQL state.

Key decisions:
- PostgreSQL is the durable source of truth.
- Redis/BullMQ is job delivery and processing infrastructure, not the canonical business store.
- Separate queues/workers for India (`ap-south-1`) and USA (`us-east-1`).
- At-least-once delivery with idempotent database effects; never claim exactly-once execution.
- Scheduler creates durable dispatch intent; it does not perform HTTP checks.
- Workers execute checks; no DB transaction stays open during an external HTTP request.
- Logical scheduled executions are distinct from BullMQ delivery/retry attempts.
- Worker concurrency, DB pools, scheduler/publisher batches, regional throughput and per-target request rates must be bounded.
- Queue-aware backpressure protects PostgreSQL and controls backlog growth.
- Regional queue limiting alone is not sufficient for per-target protection.
- Scheduler, publisher and reconciler may initially be modules in one deployable process while retaining separate responsibilities.
- Central API/PostgreSQL/Redis with regional workers is the MVP topology; this is not active-active multi-region infrastructure.

Approved Redis/BullMQ capabilities:
1. PostgreSQL transactional outbox + reliable publisher.
2. Separate India and USA queues.
3. Worker concurrency and DB pool limits.
4. Queue-aware backpressure.
5. Retries, exponential backoff and stalled-job recovery.
6. Regional rate limiting + per-target protection.
7. Idempotency + reconciliation.

Deferred:
- Redis dashboard caching.
- Plan-based job priorities.
- More than India + USA initial regions.

Important schema guardrail:
- Do **not** add speculative `claim_token`, `lease_expires_at` or `attempt_count` fields directly to `monitor_probes`.
- The execution/outbox ownership and fencing model must be designed coherently before any migration is written.

## 5. Immediate next milestone — durable dispatch design

**Next: design the transactional outbox and logical execution state machine before writing a migration.**

First inspect:
- Full region-aware monitoring migration.
- Full `monitor_checks` migration.
- Actual `monitor_probes` and `monitor_checks` schema in `nexus` and `nexus_test`.
- Current monitor service and integration-test setup.
- Existing package layout/scripts before deciding where scheduler, publisher and worker entry points live.

Design deliverables:
- Entity relationship model: probe, logical execution, outbox dispatch and check result.
- Execution and outbox state-transition tables.
- Scheduler, publisher and worker transaction boundaries.
- Safe concurrent scheduler claiming and deterministic logical execution identity.
- Ambiguous publish handling (Redis accepted job, publisher crashed before DB acknowledgement).
- Worker ownership/lease/fencing so stale workers cannot overwrite newer results.
- Retry classification, attempt/deadline policy and reconciliation rules.
- Migration/index/constraint/rollback plan.
- Integration tests for each failure boundary.

Do not create or apply the outbox migration until the design has been reviewed and agreed. The exact table names, fields and state names are intentionally still open.

## 7. Working rules

- Never commit `.env` files, credentials, Clerk/Stripe secrets or session tokens.
- Use migrations for schema changes; do not silently edit an already-applied migration.
- Keep SQL parameterized and enforce authorization/entitlements on the server.
- Treat Redis/BullMQ as delivery infrastructure, not the durable source of truth.
- Design for retries and duplicate delivery; make database effects idempotent.
- Never hold a PostgreSQL transaction open during a target HTTP request.
- Distinguish logical executions from delivery attempts.
- Record what changed, what was verified, remaining risks and the next step after each milestone.
- Protect the 21 November deadline: prioritize a reliable end-to-end monitoring path over optional polish or extra regions.
