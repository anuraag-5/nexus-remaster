## Goal

Build a production-oriented website-monitoring SaaS that demonstrates more than CRUD: secure outbound checks, durable check history, Redis/BullMQ processing, retry and recovery behavior, idempotent persistence, two-country probes (India + USA), subscription entitlements, observability, deployment and a demonstrable end-to-end workflow.

## Stack and architecture

- **Monorepo:** pnpm workspaces + Turborepo.
- **API/runtime:** Node.js 24, TypeScript, Express 5, Zod.
- **Frontend/auth:** Next.js App Router, React, Tailwind CSS v4, Clerk Core 3.
- **Database:** PostgreSQL 17 via Docker Compose, `pg`, `node-pg-migrate`.
- **Quality/ops:** Vitest, Supertest, Pino, pino-http, Helmet, graceful shutdown.
- **Planned jobs:** Redis + BullMQ with a scheduler, durable PostgreSQL dispatch/reconciliation and separate worker processes.
- **Core principles:** PostgreSQL is the durable source of truth; queue jobs may run more than once; database effects must be idempotent; enforce access and plan limits on the server; use versioned migrations, parameterized SQL, bounded work and explicit recovery paths.

## URL security — interview notes

Nexus treats submitted URLs as an **SSRF (server-side request forgery) boundary**.

- URL policy allows only HTTP/HTTPS; rejects embedded credentials, IP-literal URLs, local/internal hostname suffixes and non-standard ports; strips URL fragments.
- DNS policy checks all resolved addresses and rejects empty results or addresses not classified as ordinary public unicast.
- The checker is designed to connect to a validated IP while preserving the intended hostname for HTTP `Host` and TLS SNI/certificate verification.
- Redirect targets are revalidated; HTTPS-to-HTTP redirects are rejected; redirect count and overall check time are bounded; unnecessary response-body downloads are avoided.
- **Caveat:** These are application-layer controls, not proof of complete production security. Verify pinned-IP TLS behavior, cancellation and redirects, and add infrastructure-level egress restrictions before enabling unrestricted outbound checks.

**Interview phrasing:** “I treat monitor URLs as an SSRF boundary. Nexus validates URL structure, checks all resolved addresses, pins connections to validated IPs, and revalidates redirects. I also plan infrastructure egress controls and targeted security tests to protect against bypasses such as DNS rebinding.”

## Multi-region monitoring design — scope added

We will support **two probe regions: India and the USA**. The first proposed AWS locations are Mumbai (`ap-south-1`) and US East/N. Virginia (`us-east-1`); confirm account access, cost and deployment choice before provisioning. AWS lists both as Regions. [AWS Regions](https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions.html)

- Keep one central control plane initially (API, PostgreSQL and Redis), and deploy independent probe workers in India and the USA. These are multi-region **checks**, not active-active multi-region hosting of the entire SaaS.
- Add a `probe_regions` catalog (stable region code, country code, display name, enabled flag) instead of hard-coding region names throughout the schema.
- Add `monitor_region_assignments` so each monitor has explicit enabled probe regions. Plan entitlements will limit which assignments a workspace can create.
- Each check result must reference its `region_id` and scheduled slot. Use a database uniqueness constraint for `(monitor_id, region_id, scheduled_for)` (or equivalent durable run ID) so duplicate delivery does not create duplicate results for one scheduled slot.
- Use region-specific BullMQ queues or equivalent routing so the US worker never consumes an India-only job. Store durable dispatch intent in PostgreSQL and reconcile/publish pending work after Redis outages.
- UI should show each region’s latest status and latency separately; a single overall status must not conceal a regional outage.
- Document the central DB/Redis as remaining dependencies; regional worker deployment alone does not make the control plane highly available.

## Subscription design — scope added

Implement a small, real subscription flow in **Stripe test mode** with server-side entitlements. Live charging, tax/legal readiness and production payment onboarding are outside this sprint.

- Start with two plans (tentative): **Free** supports one region and lower monitor/retention limits; **Pro** enables India + USA and higher limits. Finalize numeric limits before implementing enforcement.
- Store plan definitions/entitlements and workspace subscription state in PostgreSQL, including Stripe customer/subscription IDs, status and billing-period/cancellation fields needed by the app.
- Add a webhook-event ledger with a unique provider event ID, so duplicate webhook delivery is idempotent.
- Checkout redirects alone must never grant paid access. Verify Stripe webhook signatures, process supported events idempotently, persist the subscription state, and enforce features/limits in the API. Stripe documents subscription lifecycle webhook events such as `customer.subscription.created`, `.updated` and `.deleted`. [Stripe event types](https://docs.stripe.com/api/events/retrieve)
- Use environment variables for Stripe secrets and price IDs. Keep secret values out of source control and logs.

## Scope control

**Must ship:** secure checker, region-aware schema and results, durable scheduling/dispatch, Redis/BullMQ, recovery/retry tests, multi-region probes in India and the USA, region-aware UI, Stripe test-mode subscriptions with idempotent webhooks and server-enforced entitlements, CI/deployment/docs.

**Defer if the deadline is threatened:** complex analytics, many notification channels, elaborate billing portal customization, Kubernetes, active-active database/Redis, and polished marketing UI. A reliable end-to-end core takes priority over breadth.
